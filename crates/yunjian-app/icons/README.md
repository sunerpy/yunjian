# 应用图标集

三步生成，一步验收，**顺序不可换**：

```bash
python3 crates/yunjian-app/icons/generate_source.py
cd crates/yunjian-app && cargo tauri icon icons/source-1024.png
python3 crates/yunjian-app/icons/generate_source.py --ico-only
cargo run -p xtask -- verify-icons
```

**第三步不是多余的。** `cargo tauri icon` 生成 `icon.ico` 的方式是把 1024 源图**降采样**，
于是脚本在 16 px 原生画出来的清晰版本根本进不了 ICO——用户在任务栏看到的仍是一张
1024 缩下来的糊图。实测对照：降采样的小层有几十种颜色（全是边缘抗锯齿混出的中间色），
原生渲染的同一层只有 **3** 种（朱砂 + 米白 + 全透明）。`--ico-only` 就是用原生层覆盖
它那一份，而 `verify-icons` 有一条颜色数上限断言专门抓「漏跑了第三步」。

设计取值（形、色、比例）的由来在 `generate_source.py` 的文件头——它们不是审美偏好，
而是由 **16 px 可辨性**反推出来的结论，包含被淘汰候选的逐条记录。

## 手写与生成产物的分工

| 文件                 | 来源                            | 说明                                                                             |
| -------------------- | ------------------------------- | -------------------------------------------------------------------------------- |
| `generate_source.py` | 手写                            | 三张 16/20/24 px 手调网格、颜色与全部机械断言。**与产物一起入库**。              |
| `source-1024.png`    | 脚本                            | 1024×1024 RGBA，喂给 `cargo tauri icon` 的源图。                                 |
| `tray.png`           | 脚本                            | 32×32 RGBA，托盘图标，按 32 px **原生**渲染。                                    |
| `icon.ico`           | 脚本（覆盖 `cargo tauri icon`） | 六层 `[32, 16, 24, 48, 64, 256]`，每层该尺寸原生渲染。                           |
| 其余全部             | `cargo tauri icon`              | `icon.png`（512×512）、`icon.icns`、Appx `Square*Logo.png`、`android/`、`ios/`。 |

**源图刻意不叫 `icon.png`。** `cargo tauri icon` 会把 `icons/icon.png` **覆写成 512×512**
（本机实测）。源图与它同名会导致下一轮拿上一轮的 512 当源，每跑一次掉一档分辨率，
而 `verify-icons` 那条「源图必须 1024×1024」的断言会莫名变红。

## 为什么必须同时有 `icon.png` 与 `icon.ico`（两条不同的代码路径各自强制）

- **`icon.png`** — `tauri-codegen` 的 `context.rs` 在 Unix 目标上无条件要求
  `icons/icon.png`（`find_icon(..., |i| i.ends_with(".png"), "icons/icon.png")`），
  缺失即编译失败。
- **`icon.ico`** — `tauri-build` 的 `lib.rs:618` 在 **Windows 目标**上从 `bundle.icon`
  里找一个以 `.ico` 结尾的项，找不到就回落 `icons/icon.ico`；文件不存在时直接报
  `` `icons/icon.ico` not found; required for generating a Windows Resource file during tauri-build ``
  并让构建失败（`lib.rs:672`）。**这条路径没有 PNG 回落**，与上面那条不同。

后者是一条**只在 Windows 上出现**的编译失败：Linux 上只有 `icon.png` 一切正常，
Windows CI 第一次跑才红。`tests/window_config.rs` 因此有一条断言两个文件都存在。

## 造型：朱底双笔印（第五版，按给定像素坐标施工）

**一块实心朱砂方印，印面上以不透明米白刻出两道等宽等高的竖笔**（白文印／阴刻），
模拟竖排诗行。四角透明、印面四周留 1 px 透明气口，没有圆角底板。

### 本版与前四版的流程差别：坐标是输入，不是产出

前四版都是「自由发挥造型 + 先画大图再缩小」，四轮全部被目视否掉。第五版把设计
自由度收回：**16×16 的逐像素坐标由需求方直接给定**，脚本只负责按坐标施工、逐档
取整、并守住可机械验证的不变量。

| 版本 | 造型                  | 被否的根因                                                                                                     |
| ---- | --------------------- | -------------------------------------------------------------------------------------------------------------- |
| v1   | 朱红圆底 + 米白月牙   | 16 px 牙尖细到亚像素而消失成白斑；红白抗锯齿混出粉雾；圆环左厚右薄                                             |
| v2   | 红框 + 三条竖条       | 最右竖条顶穿右框线；竖条下端参差；读作柱状图 / 均衡器                                                          |
| v3   | 红框 + 右下 45° 斜切  | 斜边在 16 px 退化成 1 px 碎阶梯；右框被吃掉致方框开口；框内全空，语义为空                                      |
| v4   | 实心红块 + 米白「山」 | 碎线／顶穿／开口都修好了，但仍读作柱状图；外框删净致印章意象丢失；三笔非对称；六档中两档笔画变细（未逐档取整） |

### 最终 16×16 逐像素坐标（半开区间，左上角为原点）

| 构件           | 坐标                                                    | 尺寸    |
| -------------- | ------------------------------------------------------- | ------- |
| 透明气口       | 最外一圈                                                | 1 px    |
| 朱砂印身       | `x ∈ [1, 15)`、`y ∈ [1, 15)`                            | 14×14   |
| 左笔（米白）   | `x ∈ [5, 7)`、`y ∈ [5, 11)`                             | 2×6     |
| 右笔（米白）   | `x ∈ [9, 11)`、`y ∈ [5, 11)`                            | 2×6     |
| 笔间朱缝       | `x ∈ [7, 9)`、`y ∈ [5, 11)`                             | 2×6     |
| 朱边（净间距） | 左 `x ∈ [1,5)` 右 `[11,15)` 上 `y ∈ [1,5)` 下 `[11,15)` | 各 4 px |

可核对的不变量：两笔**等宽等高**（各 2×6）· 全网格**左右镜像且上下镜像** ·
所有笔画 ≥ 2 px（笔 2、缝 2、朱边 4）· 所有净间距 ≥ 2 px（四侧朱边各 4 px）·
两笔加缝的外接框是正方形（6×6）。

### 那处 1 px 矛盾选了哪条路，以及为什么

需求方给的骨架里还有一圈 `x/y ∈ [3, 13)` 边界的 **1 px 镂空内框**，它与「笔画 ≥ 2 px、
净间距 ≥ 2 px」冲突。三条出路（a 收窄两笔 / b 去掉镂空环 / c 微调坐标凑到 2 px）里
**采用 b**，其余两条逐条排除：

- **a 与「保留镂空环的 c」不可能，这是算术不是取舍。** 保留那一圈时，一行的像素预算是
  `1 气口 + 2 朱边 + 1 镂空 + 2 净距 + 2 笔 + 2 缝 + 2 笔 + 2 净距 + 1 镂空 + 2 朱边 + 1 气口 = 18`，
  **超出 16 两格**。收窄两笔省不下这两格（笔已在 2 px 下限），且破坏左右对称。
- **「保留边框感的 c」是渲图目视否掉的，不是推理否掉的。** 把镂空换成 16 px 下唯一
  塞得进去的合法边框（最外 2 px 米白外框 + 10×10 朱面 + 2 px 净距，行预算
  `1+2+2+2+2+2+2+2+1 = 16` 零自由度），与去环版一起渲成 16/24/32 × 浅／深的放大
  对照图后逐格目视，米白外框版被否，两条理由：**朱面只剩 10×10（62.5%）而米白外框
  在浅底上对比仅 1.03:1、完全隐形**——那两圈像素在浅底纯浪费，图标目视显著变小；
  以及**跨底漂移**，同一份字节在浅底读作「一小块红方块」（外框隐形）、在深底读作
  「白框套红块」（外框显形为高对比亮边），轮廓面积、层级数、第一读全变。

**b 同时满足 c 列出的每一条要求**（两笔等宽等高、左右镜像对称、缝宽均匀、四边留白
对称、笔画 ≥ 2 px），且净间距是 4 px 而不是勉强凑到的 2 px。代价是没有独立边框线，
只有 4 px 均匀朱边——但「实心朱底 + 白色刻痕」本身就是白文印的形制。

### 逐档取整：每档独立按该档网格取整，不做浮点缩放

骨架参数是 `(气口 m, 朱边 b, 笔宽 s, 缝宽 g)`，笔高恒为 `2s + g`：

| 档位   | 缩放  | m   | b   | s（笔宽） | g（缝宽） | 笔高 | 印身          | 朱色占印面 |
| ------ | ----- | --- | --- | --------- | --------- | ---- | ------------- | ---------- |
| 16 px  | 1×    | 1   | 4   | 2         | 2         | 6    | 14 px (87.5%) | 87.8%      |
| 20 px  | 1.25× | 1   | 5   | 3         | 2         | 8    | 18 px (90.0%) | 85.2%      |
| 24 px  | 1.5×  | 2   | 6   | 3         | 2         | 8    | 20 px (83.3%) | 88.0%      |
| 32 px  | 2×    | 2   | 8   | 4         | 4         | 12   | 28 px (87.5%) | 87.8%      |
| 48 px  | 3×    | 3   | 12  | 6         | 6         | 18   | 42 px (87.5%) | 87.8%      |
| 64 px  | 4×    | 4   | 16  | 8         | 8         | 24   | 56 px (87.5%) | 87.8%      |
| 256 px | 16×   | 16  | 64  | 32        | 32        | 96   | 224 px(87.5%) | 87.8%      |

- **16 的整数倍档位**由 `MASTER_16` **精确整数倍复制**。本形全部是轴对齐矩形、没有
  斜边，整数倍复制得到数学上完全相同的形状——零抗锯齿、零比例漂移，
  `assert_scales_exactly` 逐像素复核。
- **20 与 24 px 不是 16 的整数倍，各有一份手调网格。** Windows 在通知区域与若干位置
  按这两档取图，靠缩放去凑它们正是前四版失效的入口。
- **笔宽逐档恒等于 `floor(2 × 缩放 + 0.5)`**（16→2、20→3、24→3、32→4、48→6、64→8、
  256→32）。这条在**两处各断言一遍**：`generate_source.py` 查渲染前的网格，
  `xtask verify-icons` 查**已写进 ICO 的字节**。v4 的「六档中两档笔画变细」正是缺后
  一条——当时的门禁只查层数、层序、四角 alpha 与颜色数，四项全绿。
- 20 / 24 px 的取整不是拍的：`2m + 2b + 2s + g = 边长` 且 `2m + 2b + 笔高 = 边长`，
  于是 `g` 与边长同奇偶。20 px 的 `g` 目标 2.5，可达 2 或 4，取更近的 2，随后
  `m + b = 6` 且 `b ≈ 5`（4 × 1.25），故 `m = 1, b = 5`。24 px 的 `g` 目标 3，2 与 4
  等距，取 2 后 `m + b = 8`、`b = 6`（4 × 1.5 恰好）、`m = 2`；取 4 则 `m = 1`、
  印身占 91.7%，超出 83%~90% 的取景一致区间。

### 深色模式补偿：做了，但天花板只有 2.7%

v4 的朱砂 `#D8452F` 对浅色托盘 3.93:1、对深色托盘 3.73:1——**深色侧明显更弱**。
两条候选路径逐条判定：

- **给红块加 1 px 米白外描边**：违反本版硬约束（1 px 笔画），且 1 px 在 24 px 档
  ×1.5 = 1.5 px 必然糊；加厚到 2 px 就是上面被目视否掉的外框版。**不采用。**
- **把红色提亮**：采用。单个 ICO 无法按系统主题切色（那需要运行时 `set_icon`，属
  产品代码），所以能做的是把这一个朱砂移到**浅深两侧对比相等**的点。

那个点可以解出来：设浅底相对亮度 `Ll = 0.8963`、深底 `Ld = 0.0144`，两侧相等即
`(Ll + 0.05)/(L + 0.05) = (L + 0.05)/(Ld + 0.05)`，得 `L = 0.1969`，两侧同为 **3.83:1**
——这就是**任何单色填充**在这两种托盘底色之间能取到的**最大下界**。本版取
`#DB4634`（`L = 0.1969`），米白同步提亮到 `#FAF6EE` 保住刻痕对比。

| 组合             | v4         | v5（本版） | 变化      |
| ---------------- | ---------- | ---------- | --------- |
| 朱砂 vs 浅色托盘 | 3.93:1     | 3.83:1     | −2.5%     |
| 朱砂 vs 深色托盘 | **3.73:1** | **3.83:1** | **+2.7%** |
| 米白刻痕 vs 朱砂 | 3.81:1     | 3.95:1     | +3.7%     |

**如实结论：深色侧只能净增 2.7%，因为 3.83:1 是算术上限。**
`docs/reports/icon-dark-compensation.png` 把两版配色同几何并置，就是为了让这个「弱」
可被目视核验。**实际目视结果：浅深两行的左右两格都看不出差别**——通道差只有
`(+3, +1, +5)`，低于并置可察觉阈值。这次补偿真正拿到的是「两侧对比不再一头轻一头
重」，而不是深色分离变强。要让深色分离真正变强只有两条路：浅色描边（已渲图否掉，
理由跨底漂移）或主题感知图标（产品代码，本任务禁改）。

### 刻痕为什么是不透明米白，而不是镂空

**镂空（透明）在深浅两种底色下读法会漂移。** 实测：浅色托盘上镂空显 `#F3F3F3`，
读作「纸上未着墨的字口」；深色托盘上同一枚图标的镂空变成 `#202020`，读作「打穿的孔
／镂雕金属牌」——同一个图标在两种系统主题下读成两个不同的符号。填成不透明米白后
两行读法一致。

## 机械校验清单

`generate_source.py` 的 `assert_uniform` + `assert_scales_exactly`（渲染前，逐档跑）：

反推骨架必须与参数表 `SKELETON` 逐项相同 · 只三种颜色、无中间色 · 四角透明 ·
印身为正方形且四边气口等宽 · **印面实心**（bbox 内零透明像素，v3 的空心框会红）·
朱色与刻痕的每一段都 ≥ 2 px（逐行逐列）· **刻痕不许与透明相邻**（朱边被刻穿即红，
v2 顶穿框线会红）· 四侧朱边等宽且 ≥ 2 px、缝宽 ≥ 2 px · **全网格左右镜像且上下镜像** ·
刻痕恰为**两个**四连通分量且两者 (宽, 高, 像素数) 相同 · 朱色恰为一个连通分量 ·
**笔宽 == `floor(2×缩放+0.5)`** · **笔高 == 2×笔宽 + 缝宽**（笔群外接框为正方形）·
印身占整格 83%~90% · 朱色占印面 83%~92% · 16 的整数倍档位与 16 px 定稿逐像素相同。

`xtask verify-icons`（**从已写进 ICO 的字节**反推，逐层跑）：

源图 1024×1024 且四角 alpha 全 0 · 六层齐备且层序 `[32, 16, 24, 48, 64, 256]`、
32 px 在最前（**只能靠解析目录字节发现**，图像库的 `sizes()` 返回集合、顺序在那里
就丢了）· 16/24/32 三层颜色数 ≤ 4 · 目录项尺寸与内嵌 PNG 实际尺寸一致 ·
托盘四角 alpha 为 0 · 三张表逐格底色逐字节一致 · **逐层骨架**：只出现朱砂与米白两种
实色（第三种即降采样产物，点名坐标）、两笔等宽、左右等距、上下等距、印身正方、
**笔宽 == `floor(2×缩放+0.5)`**、笔高 == 2×笔宽+缝宽、朱边与缝宽 ≥ 2 px、
印身占整格 83%~90%、**双向镜像对称**。

## 验收结论（实测，非采信生成器的成功消息）

- **源图** 1024×1024 RGBA，四角 alpha 全为 0。
- **`icon.ico` 六层齐备，层序 `[32, 16, 24, 48, 64, 256]`，32 px 在最前**。
- **每层颜色数为 3**（朱砂 + 米白 + 全透明），抗锯齿中间色为 0。
- **六层逐层骨架实测**：笔宽分别 4/2/3/6/8/32，与各档期望值 4/2/3/6/8/32 **逐档相符**；
  六层全部双向镜像对称。
- **托盘图标**四角 alpha 为 0，无自绘圆角底板。
- **三张表**：六档 `docs/reports/icon-contact-sheet.png`（1536×512）、小尺寸专用
  `docs/reports/icon-small-sizes.png`（720×480，只含 16/24/32）、深色补偿
  `docs/reports/icon-dark-compensation.png`（480×480，两版配色并置）。前两张的像素
  取自 **ICO 里真实那几层**，按整数倍最近邻放大。
- **逐格底色一致**：由 `probe_backdrops` 逐格取样断言，同一行各格基准底色逐字节相同。

### 联系表为什么要三张

六档表为让 256 px 那层按原尺寸呈现，格边长必须是 256，整张表宽 1536。看图管道一旦
把它整体缩到 1 K 以内，**缩放本身**会在红白边界混出粉雾，而造型被推翻的四轮问题
全部只出在 16/24/32 三档。小表 720×480，小到不会被任何管道再缩一次。
第三张是深色补偿的 A/B：前两张只呈现当前这一版，看不出补偿改了什么；声称做了补偿
却不给对照，与没做无法区分。

### 亲眼过目的逐档结论（16/24/32 三档 × 浅色行与深色行）

| 档位  | 浅色行 `#F3F3F3`                                                                                                 | 深色行 `#202020`                                   |
| ----- | ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 16 px | 两笔清晰、边界干净无灰过渡、目视等宽等高、顶底对齐、中缝通透不糊连；红块四边完整闭合，无开口／顶穿／碎阶梯／粉雾 | 读法与浅色行完全一致；深底下白笔对比更强、读感更锐 |
| 24 px | 同上，判断更快；缝隙相对笔宽比 16 px 略细（笔变粗而缝未同比变粗），仍明显分离                                    | 同浅色行，四边闭合、无缺陷                         |
| 32 px | 两笔清晰等宽等高、中缝相对最细但未糊连；印身最外圈 100% 朱砂（逐字节核实）                                       | 同浅色行；四周留白 22 px 完全对称（逐字节核实）    |

**浅深两行不漂移**：六格第一读完全一致，没有出现一行读成印章、另一行读成窗口。
差异只在对比感：浅底上红块轮廓更跳、白笔相对柔；深底上白笔更跳、红块轮廓相对柔。

### 已知残留（诚实记录，不粉饰）

1. **六格的第一读是「暂停按钮」，不是印章。** 两笔等高等宽是需求方指定的硬骨架，
   它避开了 v2/v4 被读成柱状图的坑（三根或不等高），但换来与暂停键同构的风险，
   而暂停键的识别特征恰恰就是「两条等长竖条居中」。本版靠「笔不通高（上下各留
   4 px 朱边）+ 实心方印」压低它，**消不掉**。这是骨架层面的取舍，不是取整或配色
   能修的东西。
2. **深色托盘上印面与背景的分离仍偏弱**（3.83:1），原因是上面那条 3.83:1 的算术上限。
3. **不认汉字或不熟悉篆刻的用户读到的是「一枚红印 + 两道白痕」**，读不出竖排诗行。

### 两次目视误判也记在这里，因为它们同样有代价

本轮的两次独立目视各出了一次几何误判，都被逐字节取样推翻：

1. 报「32 px 格的红方块右边被画布裁掉、右侧留白为 0、右边缘无法核验」，并附带
   「16 px 留白最多、32 px 零留白，各档 padding 不成比例」。字节实测：小表三格的
   四周留白分别是 **16 px→15、24 px→20、32 px→22，四侧完全相等**，且三格的印身
   最外圈都是 100% 朱砂。结论与目视**恰好相反**——32 px 留白最多，16 px 最少。
2. 报深色补偿表「下行两格的红块比上行更大、更贴边，白竖条位置随之偏移」。字节实测：
   四格**全部** 196×196、四侧留白全部 22 px，逐格相同。

**目视用来判语义，字节用来判几何，两者不可互相替代**，反过来也一样：语义结论
（「读作暂停按钮」）字节永远证不了，几何结论目视经常判错。

## 颜色

| 组合                                 | 对比度 |
| ------------------------------------ | ------ |
| 朱砂 `#DB4634` vs 浅色托盘 `#F3F3F3` | 3.83:1 |
| 朱砂 `#DB4634` vs 深色托盘 `#202020` | 3.83:1 |
| 米白 `#FAF6EE` vs 朱砂 `#DB4634`     | 3.95:1 |

**三对全过 WCAG 1.4.11 对非文本图形的 3:1 门槛**，一套图标服务两种系统主题，不发两套。
`_contrast()` 可当场复算这张表。

### 失败场景（真跑过，不是推理）

1. **把源图压平到白底**（`RGB` 无 alpha）：`verify-icons` 退出 **1**，报
   `源图必须是透明背景 ... 第 [0, 1, 2, 3] 个角不透明`。
2. **用 Pillow 从 1024 降采样写 ICO**（模拟漏跑 `--ico-only`）：退出非 0，一次报出
   3 项——16/24/32 三层的颜色数均超上限 4。

两次都已还原，还原后 `verify-icons` 退出 0、ICO 的 SHA-256 与还原前一致。

## macOS squircle：明示不处理

Apple 期望 macOS 图标是一块 squircle 底板；本图标无底板，在 Dock 里以字形形态呈现，
比相邻图标视觉上小一圈。**不处理**，理由与将来要修时的最小改动写在
`generate_source.py` 文件头末节。核心是：本机 Linux 无法目视验证 macOS 产物，
而发一份没人看过的图标比接受这个已知差异更糟。
