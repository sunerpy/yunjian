# 应用图标集

三步生成，一步验收，**顺序不可换**：

```bash
python3 crates/yunjian-app/icons/generate_source.py
cd crates/yunjian-app && cargo tauri icon icons/source-1024.png
python3 crates/yunjian-app/icons/generate_source.py --ico-only
cargo run -p xtask -- verify-icons
```

**第三步不是多余的。** `cargo tauri icon` 生成 `icon.ico` 的方式是把 1024 源图**降采样**，
于是脚本在 16 px 原生画出来的清晰版本根本进不了 ICO——用户在任务栏看到的仍是一张
1024 缩下来的糊图。实测对照：降采样的小层有几十种颜色（全是边缘抗锯齿混出的中间色），
原生渲染的同一层只有 **3** 种（朱砂 + 米白 + 全透明）。`--ico-only` 就是用原生层覆盖
它那一份，而 `verify-icons` 有一条颜色数上限断言专门抓「漏跑了第三步」。

设计取值（形、色、比例）的由来在 `generate_source.py` 的文件头——它们不是审美偏好，
而是由 **16 px 可辨性**反推出来的结论，包含被淘汰候选的逐条记录。

## 手写与生成产物的分工

| 文件                 | 来源                            | 说明                                                                             |
| -------------------- | ------------------------------- | -------------------------------------------------------------------------------- |
| `generate_source.py` | 手写                            | 三张 16/20/24 px 手调网格、颜色与全部机械断言。**与产物一起入库**。              |
| `source-1024.png`    | 脚本                            | 1024×1024 RGBA，喂给 `cargo tauri icon` 的源图。                                 |
| `tray.png`           | 脚本                            | 32×32 RGBA，托盘图标，按 32 px **原生**渲染。                                    |
| `icon.ico`           | 脚本（覆盖 `cargo tauri icon`） | 六层 `[32, 16, 24, 48, 64, 256]`，每层该尺寸原生渲染。                           |
| 其余全部             | `cargo tauri icon`              | `icon.png`（512×512）、`icon.icns`、Appx `Square*Logo.png`、`android/`、`ios/`。 |

**源图刻意不叫 `icon.png`。** `cargo tauri icon` 会把 `icons/icon.png` **覆写成 512×512**
（本机实测）。源图与它同名会导致下一轮拿上一轮的 512 当源，每跑一次掉一档分辨率，
而 `verify-icons` 那条「源图必须 1024×1024」的断言会莫名变红。

## 为什么必须同时有 `icon.png` 与 `icon.ico`（两条不同的代码路径各自强制）

- **`icon.png`** — `tauri-codegen` 的 `context.rs` 在 Unix 目标上无条件要求
  `icons/icon.png`（`find_icon(..., |i| i.ends_with(".png"), "icons/icon.png")`），
  缺失即编译失败。
- **`icon.ico`** — `tauri-build` 的 `lib.rs:618` 在 **Windows 目标**上从 `bundle.icon`
  里找一个以 `.ico` 结尾的项，找不到就回落 `icons/icon.ico`；文件不存在时直接报
  `` `icons/icon.ico` not found; required for generating a Windows Resource file during tauri-build ``
  并让构建失败（`lib.rs:672`）。**这条路径没有 PNG 回落**，与上面那条不同。

后者是一条**只在 Windows 上出现**的编译失败：Linux 上只有 `icon.png` 一切正常，
Windows CI 第一次跑才红。`tests/window_config.rs` 因此有一条断言两个文件都存在。

## 造型：朱文方印（第六版）

**一圈朱砂方框、框内米白印底、印底中央一个朱砂印文**——三层结构，也就是真实朱文印
（阳刻）的形制：边框与印文着朱，其余留白。印文取「⊤」（横在上、竖在下居中，即「丅」），
**单一连通笔画**。四角透明、印面四周留等比透明气口，没有圆角底板。

### 六版对照

| 版本 | 造型                            | 被否的根因                                                                                                     |
| ---- | ------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| v1   | 朱红圆底 + 米白月牙             | 16 px 牙尖细到亚像素而消失成白斑；红白抗锯齿混出粉雾；圆环左厚右薄                                             |
| v2   | 红框 + 三条竖条                 | 最右竖条顶穿右框线；竖条下端参差；读作柱状图 / 均衡器                                                          |
| v3   | 红框 + 右下 45° 斜切            | 斜边在 16 px 退化成 1 px 碎阶梯；右框被吃掉致方框开口；框内全空，语义为空                                      |
| v4   | 实心红块 + 米白「山」           | 仍读作柱状图；外框删净致印章意象丢失；三笔非对称；六档中两档笔画变细（未逐档取整）                             |
| v5   | 实心红块 + 两道等宽等高米白竖笔 | 字节全绿、逐档取整相符，但**第一读是暂停按钮**；且指定的 1 px 镂空内框被整条删掉，「框—内白—印文」三层从未存在 |
| v6   | 朱环 + 米白印底 + 朱砂「⊤」     | 本版。三层结构齐备并**被断言守着**；第一读是拉丁字母「T」（残留，见下）                                        |

### v5 的两条根因，本版逐条处理

**1. 内框缺失的根因：不是导出链路丢的，也不是被同色覆盖，是压根没画。**
逐字节核实链条如下：

- `generate_source.py` v5 的 `MASTER_16` 里，第 3 至 12 行是
  `.##############.` 与 `.####oo##oo####.`——**没有任何一行含内框那一圈的记号**，
  ASCII 网格本身就只有两层。
- v5 的文件头明确写了这个决定并给了算术依据：保留 1 px 镂空环时一行的像素预算是
  `1+2+1+2+2+2+2+2+1+2+1 = 18 > 16`，于是它选了「删掉环」这条路（当时标为出路 b）。
- 导出链路无罪：源图中线段序与 `MASTER_16` 逐格一致（v5 实测
  `透明1 → 朱4 → 白2 → 朱2 → 白2 → 朱4 → 透明1` 格），`cargo tauri icon` 与
  `--ico-only` 都只是忠实复制那两层。

**所以那次不是执行失误，是把「需求方指定的层」当成可协商项删掉了，而当时没有任何
断言看着「三层是否真的存在」。** 本版把它变成两条硬断言（见下面的机械校验清单）：
中线段序必须是七段 `透明→朱→内白→印文→内白→朱→透明`，且朱色必须恰为**两个**连通
分量（贴边的外环 + 不贴边的印文）。**两条都要，缺一条抓不住 v5**——v5 的中线段序在
记号上与本版完全相同（中间那段朱色是两笔之间的缝），只有连通分量数不同（v5 是 1）。
`xtask verify-icons` 有一条反向单测 `rejects_the_v5_solid_seal_with_two_bars` 直接
合成 v5 那枚层并断言它被判红。

**2. 「两道等宽等高竖笔」与暂停键同构，只能换骨架。** 暂停键的识别特征恰恰是
「两条等长竖条居中」，配色与取整都压不掉。本版换成**单一连通**的「⊤」：它上下不对称
（宽横在上、窄竖在下），既不可能读成两条等长竖条，也不可能读成柱状图（那要求两根
以上等宽竖条）。**代价是放弃上下镜像对称**——那条在 v5 里是硬约束，本版刻意反转成
「上下必须**不**对称」，理由与它在两处的实现见下。

### 最终 16×16 逐像素坐标（半开区间，左上角为原点）

| 构件             | 坐标                                                        | 尺寸  |
| ---------------- | ----------------------------------------------------------- | ----- |
| 透明气口         | 最外一圈                                                    | 1 px  |
| 朱砂外环（边框） | `x/y ∈ [1, 15)` 的边框，环宽 2                              | 2 px  |
| 米白印底（内白） | `x ∈ [3, 13)`、`y ∈ [3, 13)`                                | 10×10 |
| 印文·横（朱砂）  | `x ∈ [5, 11)`、`y ∈ [5, 7)`                                 | 6×2   |
| 印文·竖（朱砂）  | `x ∈ [7, 9)`、`y ∈ [7, 11)`                                 | 2×4   |
| 净距（内白余量） | 左 `x ∈ [3,5)` 右 `[11,13)` 上 `y ∈ [3,5)` 下 `y ∈ [11,13)` | 各 2  |

### 净间距逐项验算（需求方要核对的就是这张）

| 间距       | 起点（含）             | 终点（不含）       | 值            |
| ---------- | ---------------------- | ------------------ | ------------- |
| 左气口     | `x = 0`                | `x = 1`            | **1 px**      |
| 左环宽     | `x = 1`                | `x = 3`            | **2 px**      |
| 左净距     | `x = 3`（环内沿）      | `x = 5`（横左端）  | **2 px**      |
| 右净距     | `x = 11`（横右端）     | `x = 13`（环内沿） | **2 px**      |
| 上净距     | `y = 3`（环内沿）      | `y = 5`（横顶）    | **2 px**      |
| 下净距     | `y = 11`（竖底）       | `y = 13`（环内沿） | **2 px**      |
| 横高       | `y = 5`                | `y = 7`            | **2 px**      |
| 竖高       | `y = 7`                | `y = 11`           | **4 px**      |
| 竖宽       | `x = 7`                | `x = 9`            | **2 px**      |
| 竖两侧内白 | `x = 5→7` / `x = 9→11` | —                  | **2 px** 各侧 |

**全部 ≥ 2 px**，最小值恰为 2。左右对称可逐行核对：横 `[5,11)` 关于 `x = 8` 对称，
竖 `[7,9)` 同轴对称，外环与气口四边等宽。**上下刻意不对称**（横 2 px 在上、竖 4 px
在下），这是本版避开暂停键 / 柱状图误读的机制。

### 需求方给的坐标改了一处，唯一解由预算方程给出

需求方给的横是 `x ∈ [4, 12)`（宽 8），而外环内沿在 `x = 3`，净距只有 1 px——需求方
自己已指出这点并要求调到 ≥ 2 px。**改法没有自由度：**

```
2×气口 + 2×环宽 + 2×净距 + 横宽 = 16
2×1    + 2×2    + 2×2    + 横宽 = 16   →   横宽 = 6
```

于是横从 8 px 收到 6 px（`x ∈ [5, 11)`），两端各收进 1 px。竖向同理得
`横高 + 竖高 = 6`；取 `横高 2 / 竖高 4`（横高占印文框 1/3，与竖宽占横宽 1/3 同比），
印文外接框恰好 **6×6 正方形**（`y ∈ [5, 11)`）。**竖坐标 `x ∈ [7, 9)` 与需求方给的
完全一致**，只有横的两端各收 1 px。

### 印文为什么是「⊤」

6×6 的印文框内、左右镜像、单一连通、笔画 ≥ 2 px 的候选很少，逐条排除：

| 候选              | 排除理由                                                    |
| ----------------- | ----------------------------------------------------------- |
| 十（`+`）         | 四向全对称，读作「新建 / 添加 / 关闭」，通用动作按钮的语义  |
| 二 / 三（横条）   | 读作汉堡菜单或等号                                          |
| 山                | v4 已实测读作柱状图                                         |
| 实心小方块        | 读作停止键                                                  |
| 上 / 下（带中横） | 左右不对称，与「左右镜像」硬约束冲突                        |
| **⊤（丅）**       | **采用**：左右对称、上下不对称、单一连通、两段笔画均 ≥ 2 px |

方框内一个朱色单字正是**单字朱文印**的形制。**残留风险照实说**：不认篆刻的用户会把
它读成拉丁字母「T」或汉字「丁」——但那仍是「一枚印上刻了个字」，落在印章语义**内**；
v1~v5 的五轮误读（白斑 / 柱状图 / 空框 / 暂停键）全部落在语义**外**。

### 逐档取整：每档独立按该档网格取整，不做浮点缩放

骨架参数是 `(气口 m, 环宽 r, 净距 c, 横宽 bw, 横高 bh, 竖宽 sw, 竖高 sh)`，
两条恒等式恒成立：`2m + 2r + 2c + bw == 边长` 且 `bh + sh == bw`（印文框为正方形）：

| 档位   | 缩放  | m   | r   | c   | 横    | 竖    | 内白 | 印身          | 朱占印面 |
| ------ | ----- | --- | --- | --- | ----- | ----- | ---- | ------------- | -------- |
| 16 px  | 1×    | 1   | 2   | 2   | 6×2   | 2×4   | 10   | 14 px (87.5%) | 59.2%    |
| 20 px  | 1.25× | 1   | 3   | 2   | 8×3   | 2×5   | 12   | 18 px (90.0%) | 66.0%    |
| 24 px  | 1.5×  | 2   | 3   | 3   | 8×3   | 2×5   | 14   | 20 px (83.3%) | 59.5%    |
| 32 px  | 2×    | 2   | 4   | 4   | 12×4  | 4×8   | 20   | 28 px (87.5%) | 59.2%    |
| 48 px  | 3×    | 3   | 6   | 6   | 18×6  | 6×12  | 30   | 42 px (87.5%) | 59.2%    |
| 64 px  | 4×    | 4   | 8   | 8   | 24×8  | 8×16  | 40   | 56 px (87.5%) | 59.2%    |
| 256 px | 16×   | 16  | 32  | 32  | 96×32 | 32×64 | 160  | 224 px(87.5%) | 59.2%    |

- **16 的整数倍档位**由 `MASTER_16` **精确整数倍复制**。本形全部是轴对齐矩形、没有
  斜边，整数倍复制得到数学上完全相同的形状——零抗锯齿、零比例漂移，
  `assert_scales_exactly` 逐像素复核。
- **20 与 24 px 不是 16 的整数倍，各有一份手调网格。** Windows 在通知区域与若干位置
  按这两档取图，靠缩放去凑它们正是前四版失效的入口。
- 两条跨档取整式，`generate_source.py`（查渲染前的网格）与 `xtask verify-icons`
  （查**已写进 ICO 的字节**）**各断言一遍**：
  **气口 `m == floor(1 × 缩放 + 0.5)`**（16→1、20→1、24→2、32→2、48→3、64→4、256→16）
  且四边逐边相等；**环宽 `r == floor(2 × 缩放 + 0.5)`**（16→2、20→3、24→3、32→4、
  48→6、64→8、256→32）。v4 的「六档中两档笔画变细」正是缺后一处的字节断言——当时的
  门禁只查层数、层序、四角 alpha 与颜色数，四项全绿。
- 20 / 24 px 的取整不是拍的。由 `2(m+r+c) + bw == 边长`，`bw` 与边长同奇偶；
  由「竖居中」要求 `bw - sw` 为偶。**20 px**：`m+r+c` 理想 6.25，取 6 得 `bw = 8`
  （占格 40.0%，理想 37.5%），取 7 得 `bw = 6`（30.0%，偏小）；环宽优先满足自己的
  取整式（`r = 3`），剩下 `m = 1, c = 2`。**24 px**：`m+r+c` 理想 7.5，取 7 得
  `bw = 10` 但 `m = 1`、印身占 91.7% 超出 83%~90% 的取景区间；取 8 得 `bw = 8` 且
  `m = 2` 命中气口取整式，故 `m = 2, r = 3, c = 3`。两档 `sw` 取 2
  （`2/8 = 0.25` 比 `4/8 = 0.5` 更接近定稿的 `2/6 = 0.333`）、`bh` 取 3
  （`3/8 = 0.375` 比 `2/8` 更接近 0.333）。

### 深色模式补偿：做了，但天花板只有 2.7%

v4 的朱砂 `#D8452F` 对浅色托盘 3.93:1、对深色托盘 3.73:1——**深色侧明显更弱**。
两条候选路径逐条判定：

- **给红块加 1 px 米白外描边**：违反本版硬约束（1 px 笔画），且 1 px 在 24 px 档
  ×1.5 = 1.5 px 必然糊。**不采用。**
- **把红色提亮**：采用。单个 ICO 无法按系统主题切色（那需要运行时 `set_icon`，属
  产品代码），所以能做的是把这一个朱砂移到**浅深两侧对比相等**的点。

那个点可以解出来：设浅底相对亮度 `Ll = 0.8963`、深底 `Ld = 0.0144`，两侧相等即
`(Ll + 0.05)/(L + 0.05) = (L + 0.05)/(Ld + 0.05)`，得 `L = 0.1969`，两侧同为 **3.83:1**
——这就是**任何单色填充**在这两种托盘底色之间能取到的**最大下界**。取
`#DB4634`（`L = 0.1969`），米白同步提亮到 `#FAF6EE` 保住印文对比。

| 组合             | v4         | v5 / v6    | 变化      |
| ---------------- | ---------- | ---------- | --------- |
| 朱砂 vs 浅色托盘 | 3.93:1     | 3.83:1     | −2.5%     |
| 朱砂 vs 深色托盘 | **3.73:1** | **3.83:1** | **+2.7%** |
| 米白印底 vs 朱砂 | 3.81:1     | 3.95:1     | +3.7%     |

**如实结论：深色侧只能净增 2.7%，因为 3.83:1 是算术上限。**
`docs/reports/icon-dark-compensation.png` 把两版配色同几何并置，就是为了让这个「弱」
可被目视核验。**实际目视结果：浅深两行的左右两格差别极弱**——朱砂通道差只有
`(+3, +1, +5)`；米白那 `(+5, +7, +13)` 在**深色行**能勉强看出右列印底略偏暖，浅色行
看不出。这次补偿真正拿到的是「两侧对比不再一头轻一头重」。要让深色分离真正变强只有
两条路：浅色描边（v5 已渲图否掉，理由跨底漂移）或主题感知图标（产品代码，本任务禁改）。

### 米白印底在浅色托盘上近乎隐形，这是已知取舍且配色空间为空

米白 `#FAF6EE` 对浅色托盘 `#F3F3F3` 只有 1.03:1，所以浅色托盘上图标读作「朱色方框 +
框内一个朱色字」，深色托盘上印底显形为一块亮白，读作「白纸上盖了一枚朱文印」。

这与 v5 渲图否掉的那个「2 px 米白**外**框」变体**不是同一种缺陷**：那个变体把米白放
最外圈，浅底上图标外轮廓本身消失、目视尺寸从 14×14 掉到 10×10，轮廓面积与第一读全变
（跨底漂移）。本版最外圈是朱砂，**两种底色下轮廓位置、面积、第一读完全相同**，差别
只在框内那块底是否显形——已由并置对照图目视确认。

要让浅底上印底也显形，需要同时满足「对浅底 ≥ 3:1」与「对朱砂 ≥ 3:1」的颜色：
朱砂 `L = 0.1969`，对它 3:1 要求 `L ≥ 0.741` 或 `L ≤ 0.0157`；对浅底（`L = 0.8963`）
3:1 要求 `L ≤ 0.2488`。两区间只在 `L ≤ 0.0157` 相交，即印底得是近黑色——那就不是印章。
**所以这不是取舍不当，是配色空间为空。**

### 印底为什么是不透明米白，而不是镂空

**镂空（透明）在深浅两种底色下读法会漂移。** 实测：浅色托盘上镂空显 `#F3F3F3`，
读作「纸上未着墨的字口」；深色托盘上同一枚图标的镂空变成 `#202020`，读作「打穿的孔
／镂雕金属牌」——同一个图标在两种系统主题下读成两个不同的符号。填成不透明米白后，
深底上它是一块白纸、浅底上它与纸同色，两种读法都落在「印在纸上」这一个语义里。

## 机械校验清单

`generate_source.py` 的 `assert_uniform` + `assert_scales_exactly`（渲染前，逐档跑）：

反推骨架必须与参数表 `SKELETON` 逐项相同 · 两条恒等式独立复算
（`2m+2r+2c+bw == 边长`、`bh+sh == bw`）· 只三种颜色、无中间色 · 四角透明 ·
**水平与竖直中线段序都必须是 `透明→朱→内白→印文→内白→朱→透明`** ·
印身为正方形且**四边气口逐边相等** · **气口 == `floor(1×缩放+0.5)`** ·
**环宽 == `floor(2×缩放+0.5)`** · 印面实心（bbox 内零透明像素，v3 的空心框会红）·
朱色与米白的每一段都 ≥ 2 px（逐行逐列）· **印文四向净距 ≥ 2 px 且左右相等、上下相等** ·
米白不许与透明相邻（外环被穿透即红，v2 顶穿框线会红）· **左右镜像且上下必须不镜像** ·
**朱色恰为两个连通分量（外环 + 印文）**、米白恰为一个 · 印文单一连通且横比竖宽、
竖比横高、`bw - sw` 为偶（竖能居中）· 印身占整格 83%~90% ·
**朱色占印面 55%~70%**（上界守「印文糊成实心朱面」，v4/v5 的 87.8% 会红）·
16 的整数倍档位与 16 px 定稿逐像素相同。

`xtask verify-icons`（**从已写进 ICO 的字节**反推，逐层跑）：

源图 1024×1024 且四角 alpha 全 0 · 六层齐备且层序 `[32, 16, 24, 48, 64, 256]`、
32 px 在最前（**只能靠解析目录字节发现**，图像库的 `sizes()` 返回集合、顺序在那里
就丢了）· 16/24/32 三层颜色数 ≤ 4 · 目录项尺寸与内嵌 PNG 实际尺寸一致 ·
托盘四角 alpha 为 0 · 三张表逐格底色逐字节一致 ·
**逐格四周留白逐边相等且占格落在 10%~14.5%**（新增，见下）· **逐层骨架**：
只出现朱砂与米白两种实色（第三种即降采样产物，点名坐标）、
**两条中线段序都是七段**、**朱色恰两个连通分量**、印身正方、四边气口相等、
**气口 == `floor(1×缩放+0.5)`**、**环宽 == `floor(2×缩放+0.5)`**、印文框为正方形、
净距与笔画 ≥ 2 px、印文是「⊤」的形（横比竖宽、竖比横高）、印身占整格 83%~90%、
**左右镜像且上下不镜像**。

### 「内框真实存在」这条断言长什么样

两条合起来才够，缺一条抓不住 v5：

1. **中线段序**（`MIDLINE` 常量）：把水平与竖直中线各折成段序列，记号序必须严格等于
   `[透明, 朱, 内白, 朱, 内白, 朱, 透明]`。
2. **朱色连通分量恰为 2**：贴着印身左边的那个是外环，不贴边的那个是印文。

**为什么两条都要**：v5 的中线段序在记号上与本版一模一样（中间那段朱色是两道竖笔之间
的缝），只有连通分量数不同（v5 的朱色是**一个**分量——实心印面）。反过来，只查分量数
也不够：印文若贴到环上会并成一个分量，段序会掉成五段而分量数看着仍可能是 2。
单测 `rejects_the_v5_solid_seal_with_two_bars` 合成 v5 那枚层并断言它被判红。

### 联系表的格边长从 256 改成 288，因为上一版留白不等比

`verify-icons` 用整数倍最近邻把每层放大铺进格子。上一版格边长 256 且倍率**向下取整**，
于是能整除 256 的四档（16/32/64/256）绘制区正好填满格子、四周只剩图标自己那圈气口
放大后的 16 px（占格 6.2%），而不能整除的两档（24/48）反而多出居中留白（28 / 23 px，
10.9% / 9.0%）。同一张表里留白差 1.75 倍，目视读成「有几档的红块上下直接顶到画布边、
各档 padding 不成比例」——需求方本轮点名的就是这个。

修法两处：格边长改 **288**（= 256 + 2×16，仍让 256 px 那层按原尺寸呈现），
倍率按「目标绘制区 `side × 8 / 9`」**四舍五入**而不是向下取整（24 px 因此取 11 倍
得 264，而不是 10 倍得 240）。改后逐格实测：

| 档位   | 留白（px） | 占格      |
| ------ | ---------- | --------- |
| 16 px  | 32         | 11.1%     |
| 24 px  | 34         | 11.8%     |
| 32 px  | 32         | 11.1%     |
| 48 px  | 39         | **13.5%** |
| 64 px  | 32         | 11.1%     |
| 256 px | 32         | 11.1%     |

48 px 那档最大，因为它的整数倍率只能取 5（绘制区 240 比别档小）。`probe_cell_margins`
断言逐格四边相等且占格落在 10%~14.5%，把「等比」变成可判定的而不是靠目视比相邻格。

## 验收结论（实测，非采信生成器的成功消息）

- **源图** 1024×1024 RGBA，四角 alpha 全为 0。
- **源图中线七段齐备**（1 格 = 64 px）：水平
  `透明1格 → 朱2 → 内白4 → 朱2 → 内白4 → 朱2 → 透明1`；竖直
  `透明1 → 朱2 → 内白2 → 朱6 → 内白2 → 朱2 → 透明1`。托盘图同形（1 格 = 2 px）。
  **这正是 v5 缺的那一层，现在它在字节里可数。**
- **`icon.ico` 六层齐备，层序 `[32, 16, 24, 48, 64, 256]`，32 px 在最前**。
- **每层颜色数为 3**（朱砂 + 米白 + 全透明），抗锯齿中间色为 0。
- **六层逐层骨架实测**：气口 2/1/2/3/4/16 与期望 2/1/2/3/4/16 逐档相符；
  环宽 4/2/3/6/8/32 与期望逐档相符；六层全部左右镜像且上下不对称；
  两条中线段序全部七段。
- **托盘图标**四角 alpha 为 0，无自绘圆角底板。
- **三张表**：六档 `docs/reports/icon-contact-sheet.png`（1728×576）、小尺寸专用
  `docs/reports/icon-small-sizes.png`（864×576，只含 16/24/32）、深色补偿
  `docs/reports/icon-dark-compensation.png`（576×576，两版配色并置）。前两张的像素
  取自 **ICO 里真实那几层**，按整数倍最近邻放大。
- **逐格底色一致 + 逐格留白等比**：`probe_backdrops` 与 `probe_cell_margins` 各一条断言。

### 联系表为什么要三张

六档表为让 256 px 那层按原尺寸呈现，格边长必须 ≥ 256，整张表宽 1728。看图管道一旦把
它整体缩到 1 K 以内，**缩放本身**会在红白边界混出粉雾，而造型被推翻的五轮问题全部只
出在 16/24/32 三档。小表 864×576，小到不会被任何管道再缩一次。第三张是深色补偿的
A/B：前两张只呈现当前这一版，看不出补偿改了什么；声称做了补偿却不给对照，与没做无法区分。

### 亲眼过目的逐档结论（16/24/32 三档 × 浅色行与深色行）

| 档位  | 浅色行 `#F3F3F3`                                                                                                                                                                       | 深色行 `#202020`                                                                               |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 16 px | **三层清晰可辨**：朱环闭合、框内一块米白、白底中央一个朱色「⊤」。边界干净无灰过渡、无碎线／顶穿／开口／粉雾。四周留白明显，红块不贴任何画布边。印底与背景近乎同色，读作「朱框 + 朱字」 | 读法与浅色行一致，且**印底显形为一块亮白**，读作「白纸上一枚朱印」。白底让朱环与朱字的轮廓更锐 |
| 24 px | 同上，判断更快。横的两端相对内白略宽（横 8 于内白 14），竖仍居中，「⊤」形无歧义。留白 34 px，与别档目视一致                                                                            | 同浅色行，四边闭合、无缺陷。印底面积最大的一档，白纸感最足                                     |
| 32 px | 同上，最清晰的一档。竖比 16 px 档相对更粗（4 于 20 内白）但仍明显窄于横，「⊤」形正确。留白 32 px                                                                                       | 同浅色行；朱环 4 px 在深底上是最跳的一档                                                       |

**浅深两行不漂移**：六格第一读完全一致，都是「方框 + 框内一个 T 形字」。差异只在印底
是否显形（浅底隐形、深底显形），而**轮廓位置、面积、层级数三行相同**——这正是本版把
最外圈放朱砂而不是米白的目的（v5 那个米白外框变体在这一项上会漂移）。

**与 v5 的第一读对比（本轮最重要的一条目视结论）**：v5 六格读作暂停按钮（红底 +
两条等长白竖条）；本版六格读作**一个方框里的字母「T」**。暂停键的误读消失了，
换来的是「T」这个字母误读——见下面的残留第 1 条。

### 已知残留（诚实记录，不粉饰）

1. **第一读是拉丁字母「T」，不是「一枚印章」。** 「⊤」在 6×6 网格里与大写 T 同形，
   这不可避免——但它落在「印上刻了个字」的语义内，而 v1~v5 的误读（白斑 / 柱状图 /
   空框 / 暂停键）全部落在语义外。**换成任何真实汉字都需要更大的网格**：16 px 的
   10×10 内白装不下两笔以上且每笔 ≥ 2 px 的汉字（那需要至少 3 条 2 px 笔画 + 2 条
   2 px 缝 = 10 px，恰好占满、零净距）。
2. **浅色托盘上米白印底近乎隐形**（1.03:1），成因是上面那条配色空间为空。
3. **深色托盘上朱砂与背景的分离偏弱**（3.83:1），成因是那条 3.83:1 的算术上限。
4. **不认篆刻的用户读不出「朱文印」这个形制**，只读到「红框 + 红字」。这对品牌识别
   够用，对语义传达不够。

### 前几轮的目视误判也记在这里，因为它们同样有代价

v5 那轮的两次独立目视各出一次**几何误判**，都被逐字节取样推翻（详见 git 历史里
上一版本文件）。**但本轮需求方报的「四档贴边、各档 padding 不一致」是真的**，
逐格字节实测 6.2% / 10.9% / 6.2% / 9.0% / 6.2% / 6.2%，与目视一致。

**结论仍是那条，但要补一个方向**：目视判语义、字节判几何；而**当目视报几何问题时，
先用字节复核再决定信谁**——上一轮字节推翻了目视，本轮字节证实了目视。两个方向都发生
过，所以不能凭「上次目视错了」就默认这次也错。

### 失败场景（真跑过，不是推理）

**把源图压平到白底**（`RGB` 无 alpha）：`verify-icons` 退出 **1**，报
`源图必须是透明背景 ... 第 [0, 1, 2, 3] 个角不透明`。已还原，还原后 `verify-icons`
退出 0 且源图 SHA-256 与还原前逐字节一致。

## macOS squircle：明示不处理

Apple 期望 macOS 图标是一块 squircle 底板；本图标无底板，在 Dock 里以字形形态呈现，
比相邻图标视觉上小一圈。**不处理**，理由与将来要修时的最小改动写在
`generate_source.py` 文件头末节。核心是：本机 Linux 无法目视验证 macOS 产物，
而发一份没人看过的图标比接受这个已知差异更糟。
