# 应用图标集

三步生成，一步验收，**顺序不可换**：

```bash
python3 crates/yunjian-app/icons/generate_source.py
cd crates/yunjian-app && cargo tauri icon icons/source-1024.png
python3 crates/yunjian-app/icons/generate_source.py --ico-only
cargo run -p xtask -- verify-icons
```

**第三步不是多余的。** `cargo tauri icon` 生成 `icon.ico` 的方式是把 1024 源图**降采样**，
于是脚本在 16 px 原生画出来的清晰版本根本进不了 ICO——用户在任务栏看到的仍是一张
1024 缩下来的糊图。实测对照：降采样的小层有几十种颜色（全是边缘抗锯齿混出的中间色），
原生渲染的同一层只有 **3** 种（朱砂 + 米白 + 全透明）。`--ico-only` 就是用原生层覆盖
它那一份，而 `verify-icons` 有一条颜色数上限断言专门抓「漏跑了第三步」。

设计取值（形、色、比例）的由来在 `generate_source.py` 的文件头——它们不是审美偏好，
而是由 **16 px 可辨性**反推出来的结论，包含被淘汰候选的逐条记录。

## 手写与生成产物的分工

| 文件                 | 来源                            | 说明                                                                             |
| -------------------- | ------------------------------- | -------------------------------------------------------------------------------- |
| `generate_source.py` | 手写                            | 三张 16/20/24 px 手调网格、颜色与全部机械断言。**与产物一起入库**。              |
| `source-1024.png`    | 脚本                            | 1024×1024 RGBA，喂给 `cargo tauri icon` 的源图。                                 |
| `tray.png`           | 脚本                            | 32×32 RGBA，托盘图标，按 32 px **原生**渲染。                                    |
| `icon.ico`           | 脚本（覆盖 `cargo tauri icon`） | 六层 `[32, 16, 24, 48, 64, 256]`，每层该尺寸原生渲染。                           |
| 其余全部             | `cargo tauri icon`              | `icon.png`（512×512）、`icon.icns`、Appx `Square*Logo.png`、`android/`、`ios/`。 |

**源图刻意不叫 `icon.png`。** `cargo tauri icon` 会把 `icons/icon.png` **覆写成 512×512**
（本机实测）。源图与它同名会导致下一轮拿上一轮的 512 当源，每跑一次掉一档分辨率，
而 `verify-icons` 那条「源图必须 1024×1024」的断言会莫名变红。

## 为什么必须同时有 `icon.png` 与 `icon.ico`（两条不同的代码路径各自强制）

- **`icon.png`** — `tauri-codegen` 的 `context.rs` 在 Unix 目标上无条件要求
  `icons/icon.png`（`find_icon(..., |i| i.ends_with(".png"), "icons/icon.png")`），
  缺失即编译失败。
- **`icon.ico`** — `tauri-build` 的 `lib.rs:618` 在 **Windows 目标**上从 `bundle.icon`
  里找一个以 `.ico` 结尾的项，找不到就回落 `icons/icon.ico`；文件不存在时直接报
  `` `icons/icon.ico` not found; required for generating a Windows Resource file during tauri-build ``
  并让构建失败（`lib.rs:672`）。**这条路径没有 PNG 回落**，与上面那条不同。

后者是一条**只在 Windows 上出现**的编译失败：Linux 上只有 `icon.png` 一切正常，
Windows CI 第一次跑才红。`tests/window_config.rs` 因此有一条断言两个文件都存在。

## 造型：朱底白文「山」印（第四版）

**一块实心朱砂方印，印面上以不透明米白刻出汉字「山」（白文印／阴刻）。** 三竖高度
**刻意不等**——中竖最高、右竖次高、左竖最短，即真实楷书字形。

### 方法论：从 16 px 网格反推，而不是先画大图再缩小

**前三版全部死在同一个流程错误上：先画 1024 母图，再靠取整规则往下缩。** 第四版把
流程倒过来：

1. 先在 **16×16 的像素网格上逐像素定稿**（`MASTER_16`，一张可直接读的 ASCII 图）。
2. **16 的整数倍档位用精确整数倍复制**。本形全部由轴对齐矩形构成、没有任何斜边，
   所以整数倍复制得到数学上完全相同的形状——零抗锯齿、零比例漂移，
   `assert_scales_exactly` 逐像素复核。
3. **20 px 与 24 px 不是 16 的整数倍，各自另有一份手调网格**。Windows 在通知区域与
   若干位置按这两档取图，靠缩放去凑它们正是前三版失效的入口。

### 被否的前三版与它们的根因

| 版本 | 造型                   | 被否的根因                                                                         |
| ---- | ---------------------- | ---------------------------------------------------------------------------------- |
| v1   | 朱红圆底 + 米白月牙    | 月牙负空间在 16 px 细到亚像素级，牙尖消失成白斑；红白抗锯齿混出粉雾                |
| v2   | 红方框 + 三条竖条      | 右条顶穿右框线、三条长短参差、读作柱状图/均衡器；框线比例逐档跳变                  |
| v3   | 红方框 + 右下 45° 切角 | 16 px 斜边退化成一串 1 px 碎阶梯、右框被切角吃掉致方框读作开口；框内全空，语义为空 |

v3 的根因值得单列：它用**删掉内部元素**去解决 v2 的错误语义，结果是**用「没有语义」
替换「错误语义」**——第一读变成「折角文档 / dog-ear 便签」，在任务栏里与一堆通用文档
图标无法区分。

### 本轮逐条淘汰的候选（30+ 个，全部按放大对照图目视，不是推理）

| 造型                   | 第一读                                              |
| ---------------------- | --------------------------------------------------- |
| 两条全高白竖槽         | 暂停按钮                                            |
| 三条白竖槽             | 柱状图 / 均衡器（= v2 根因）                        |
| 三条白横槽（「三」）   | 汉堡菜单                                            |
| 白「回」环（同心方框） | 二维码定位点                                        |
| 点阵（两列三行 2×2）   | 六点盲文 / 骰子 / 拖拽手柄                          |
| 白「工」               | 拉丁字母 I                                          |
| 白「丁」               | 拉丁字母 T                                          |
| 白「王」               | 汉字，但与古典诗词无语义关联，且第二读撞列表/均衡器 |
| **左右对称的白「山」** | **柱状图 / 西里尔 Ш**（本轮第五次目视推翻）         |
| **非对称白「山」**     | **一枚红印上刻着一个汉字** ← 定稿                   |

「山」是唯一第一读就是汉字的候选：有横竖相交（篆刻可读性的关键），不撞拉丁字母、
不撞 UI 控件，且**语义正好落在山水诗上**。

### 刻痕为什么是不透明米白，而不是镂空

**镂空（透明）在深浅两种底色下读法会漂移。** 实测：浅色托盘上镂空显 `#F3F3F3`，
读作「纸上未着墨的字口」；深色托盘上同一枚图标的镂空变成 `#202020`，读作「打穿的孔
/ 镂雕金属牌」——同一个图标在两种系统主题下读成两个不同的符号。填成不透明米白后
两行读法一致。

### 三竖不等高与「左右镜像对称」互斥

v2 的三竖长短参差是无意的 bug，当时的补救是加一条**逐像素镜像对称**断言。本版把它
换成更准的两条，因为镜像对称会顺手禁掉真实「山」的三竖不等高，而三竖等高正是本轮
第五次被推翻的成因：

- 刻痕外接框在印身内**左右等距、上下等距**（这才是「右条顶穿右框线」真正要防的）；
- 逐行刻痕段数序列**恰好** `[1, 2, 3, 1]`：中竖先单独出头 → 右竖加入 → 左竖加入 →
  底横通宽。对称版是 `[1, 3, 1]`，三竖槽是 `[3]`，汉堡菜单是 `[1]`，全部直接变红。

| ------ | ------------- | ----- | ----- | -------- | ---------------- | ---------- |
| 16 px  | 14 px (87.5%) | 2 px  | 2 px  | 2 px     | 8:6:4            | 71.4%      |
| 20 px  | 18 px (90.0%) | 3 px  | 2 px  | 3 px     | 9:7:5            | 75.9%      |
| 24 px  | 20 px (83.3%) | 3 px  | 2 px  | 4 px     | 11:8:6           | 77.0%      |
| 32 px  | 28 px (87.5%) | 4 px  | 4 px  | 4 px     | 16:12:8          | 71.4%      |
| 48 px  | 42 px (87.5%) | 6 px  | 6 px  | 6 px     | 24:18:12         | 71.4%      |
| 64 px  | 56 px (87.5%) | 8 px  | 8 px  | 8 px     | 32:24:16         | 71.4%      |
| 256 px | 224 px(87.5%) | 32 px | 32 px | 32 px    | 128:96:64        | 71.4%      |

**没有任何一档出现小于 2 px 的笔画或净空。** 三竖露出底横以上的高度比跨档恒为
`1 : 0.75 : 0.5`（20/24 px 是取整后的 0.78/0.56 与 0.73/0.55，容差 ±0.09）。
印身占比目标 87.5%，20 与 24 px **命中不了**（要求 17.5 与 21 px，等边距做不出来），
各取可达值里更合适的一个，逐条推导在 `generate_source.py` 的约束 6.5。

## 机械校验的十三条（`assert_uniform` + `assert_scales_exactly`，逐档跑）

颜色数 ≤ 3 且无中间色 · 四角透明 · **印面实心**（内部零透明像素，v3 的空心框会红） ·
朱色与刻痕的每一段都 ≥ 2 px（逐行逐列） · **刻痕不许与透明相邻**（朱边被刻穿即红） ·
朱边四侧各 ≥ 2 px · 刻痕外接框左右等距、上下等距 · 刻痕恰为**一个**四连通分量
（点阵会红） · 朱色恰为一个连通分量 · 朱色占印面 55%~85% · 印身占整格 83%~90% ·
逐行刻痕段数序列恰为 `[1, 2, 3, 1]` 且三竖高度中 > 右 > 左且比例跨档一致 ·
底横通宽 · 16 的整数倍档位与 16 px 定稿逐像素相同。

## 验收结论（实测，非采信生成器的成功消息）

- **源图** 1024×1024 RGBA，四角 alpha 全为 0。
- **`icon.ico` 六层齐备，层序 `[32, 16, 24, 48, 64, 256]`，32 px 在最前**。层序**只能
  靠解析目录字节发现**：图像库的 `sizes()` 之类接口返回集合，顺序在那里就丢了。
- **每层颜色数为 3**（朱砂 + 米白 + 全透明），抗锯齿中间色为 0。
- **托盘图标**四角 alpha 为 0，无自绘圆角底板。
- **两张联系表**：六档 `docs/reports/icon-contact-sheet.png`（1536×512）与小尺寸专用
  `docs/reports/icon-small-sizes.png`（720×480，只含 16/24/32）。像素取自 **ICO 里真实
  那几层**，按整数倍最近邻放大。
- **逐格底色一致**：两张表都由 `probe_backdrops` 逐格取样断言过，同一行各格的基准
  底色逐字节相同。

### 联系表为什么改成一整片连续底色，以及为什么要两张

上一版在格与格之间铺中灰间隙。整数倍率让各档绘制区大小不一（16 px 铺进 256 的格子
恰好填满，24 px 只能取 10 倍得到 240、两侧各留 8 px），于是**有的格子四周多一圈底色、
有的直接顶到中灰**——同一行各格呈现的底色面积因此不同，人眼读成「各格明度不一致」，
并据此判定生成流程有 bug。**字节层其实完全相同**（逐格取样：每格恰好两种颜色，
浅色行全部 `#F3F3F3`，深色行全部 `#202020`）。去掉间隙后一行是一整片均匀底色，
每个图标周围环境完全相同，且 `probe_backdrops` 把这条变成断言而不是承诺。

第二张小表的理由是另一个观看路径问题：六档表为让 256 px 那层按原尺寸呈现，格边长
必须是 256，整张表宽 1536。看图管道一旦把它整体缩到 1 K 以内，**缩放本身**会在红白
边界混出粉雾，而造型被推翻的四轮问题全部只出在 16/24/32 三档。小表 720×480，
小到不会被任何管道再缩一次。

### 亲眼过目的逐档结论（16/24/32 三档 × 浅色行与深色行）

| 档位  | 浅色行 `#F3F3F3`                                                                                          | 深色行 `#202020`                                     |
| ----- | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 16 px | 四构件（三竖 + 底横）完整，竖间红缝通透，无糊连、无碎阶梯；第一读是「红方印上一个白记号」，「山」需第二读 | 读法与浅色行完全一致；差别只在方印外轮廓对比稍弱     |
| 24 px | 「山」识别几乎即时，三竖间隙清楚                                                                          | 同浅色行，清晰                                       |
| 32 px | 明确是「山」，笔形关系最清楚，是三档中最好的一档                                                          | 同浅色行；印面闭合，最外圈 100% 朱砂（已逐字节核实） |

**已知残留，如实记录**：

1. **16 px 下「山」语义降级。** 两轮独立目视都判第一读偏「柱状图 / 三根柱子」，
   汉字属性要第二读才成立。这是字形在低分辨率下与图表图标同构，**再调像素解决不了**。
   印章属性（正方 + 饱和朱砂 + 白色负形）在 16 px 仍然站得住。
2. **深色托盘上印面与背景的分离偏弱**。朱砂对 `#202020` 3.73:1，方印边界发虚，
   物件感下降。加浅色描边会破坏「无底板」这条硬性验收项，故不加。
3. **不认汉字的用户读不出「山」**，只到「一枚红印章 + 某个东方文字」。
   这对品牌识别够用，对语义传达不够——诚实的取舍，候选里没有任何造型两边都占。

一次目视误判也记在这里，因为它同样有代价：有一轮报「32 px 层右侧被裁、白横顶穿朱边、
右下角开口不闭合」并判为阻塞。逐字节取样推翻了它——**六格印面最外圈全部 100% 朱砂，
四周留白完全相等**（16 px 各 15、24 px 各 20、32 px 各 22 渲染像素）。
**目视用来判语义，字节用来判几何，两者不可互相替代**，反过来也一样。

## 颜色

| 组合                                 | 对比度 |
| ------------------------------------ | ------ |
| 朱砂 `#D8452F` vs 浅色托盘 `#F3F3F3` | 3.93:1 |
| 朱砂 `#D8452F` vs 深色托盘 `#202020` | 3.73:1 |
| 米白 `#F5EFE1` vs 朱砂 `#D8452F`     | 3.81:1 |

**两侧都过 WCAG 1.4.11 对非文本图形的 3:1 门槛**，一套图标服务两种系统主题，不发两套。
更暗的 `#C0362C` 浅色侧能到 4.97:1，代价是深色侧只有 2.95:1，深色行小档因此发闷。
`_contrast()` 可当场复算这张表。

### 失败场景（真跑过，不是推理）

1. **把源图压平到白底**（`RGB` 无 alpha）：`verify-icons` 退出 **1**，报
   `源图必须是透明背景 ... 第 [0, 1, 2, 3] 个角不透明`。
2. **用 Pillow 从 1024 降采样写 ICO**（模拟漏跑 `--ico-only`）：退出非 0，一次报出
   3 项——16/24/32 三层的颜色数均超上限 4。

两次都已还原，还原后 `verify-icons` 退出 0、ICO 的 SHA-256 与还原前一致。

## macOS squircle：明示不处理

Apple 期望 macOS 图标是一块 squircle 底板；本图标无底板，在 Dock 里以字形形态呈现，
比相邻图标视觉上小一圈。**不处理**，理由与将来要修时的最小改动写在
`generate_source.py` 文件头末节。核心是：本机 Linux 无法目视验证 macOS 产物，
而发一份没人看过的图标比接受这个已知差异更糟。
